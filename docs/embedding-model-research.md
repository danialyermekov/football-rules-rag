# Кандидаты embedding-моделей для RU/EN retrieval

Проверено по первоисточникам 23 октября 2026 года. Это исследование кандидатов, а не результаты нового эксперимента: модели не скачивались, API не вызывался.

## Рекомендация

Сравнить с BGE-M3 две локальные модели: сначала `Qwen/Qwen3-Embedding-0.6B`, затем `intfloat/multilingual-e5-large`. Они представляют разные подходы: decoder с инструкцией и encoder с фиксированными префиксами. Google оставить дополнительным API-кандидатом. Сам факт смены модели улучшения не гарантирует.

## Локальные кандидаты

| Кандидат | Проверенные свойства | Правильный retrieval-вход | Зачем проверять |
|---|---|---|---|
| `Qwen/Qwen3-Embedding-0.6B` | 0.6B параметров; 100+ языков; 32K вход; 32–1024 измерения; Apache-2.0 | Запрос с `Instruct: …\nQuery:…`; документ без инструкции; нормализованные embeddings, last-token pooling | Более новая инструкция-ориентированная архитектура; первая приоритетная альтернатива |
| `intfloat/multilingual-e5-large` | XLM-R encoder, 24 слоя; около 0.6B параметров; 1024 измерения; до 512 токенов; MIT | `query: ` для вопросов и `passage: ` для документов, включая RU; mean pooling и нормализация | Сильный самостоятельный multilingual encoder-контроль |

Источники свойств и форматов: [Qwen model card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B), [E5 model card](https://huggingface.co/intfloat/multilingual-e5-large).

Qwen рекомендует английскую инструкцию даже при вопросах на других языках. Для первого запуска использовать одну заранее записанную инструкцию, одинаковую по смыслу для RU/EN, без подстройки под каждый вопрос. Model card требует `transformers>=4.51.0`, `sentence-transformers>=2.7.0`; FlashAttention указан как рекомендация, не обязательная зависимость. В проекте уже есть Sentence Transformers, но совместимость конкретного lockfile и CUDA-пути надо проверить пробным запуском. [Qwen usage](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B#usage).

Английский и русский перечислены среди языков базового Qwen3; embedding-card заявляет наследование multilingual возможностей. Это не отдельная гарантия качества на русских футбольных правилах. У E5 есть опубликованные retrieval-результаты для `ru` и `en` на MIRACL. [Qwen3 languages](https://qwenlm.github.io/blog/qwen3/#key-features), [E5 technical report, table 6](https://arxiv.org/html/2402.05672v1).

Не обещаем размещение в 6 GB VRAM без измерения. Для порядка величины: 0.6B × 4 байта ≈ 2.4 GB только весов FP32; активации, allocator, CUDA и токенизация добавляют память. Загружать по одной модели, начать с малого batch, записать пик памяти и задержку. Для E5 заранее проверить все чанки его токенизатором с префиксом: 1000 символов не гарантируют ≤512 токенов; молчаливое truncation сделает сравнение некорректным.

32K у Qwen не причина менять размер текущих коротких чанков: в первом сравнении чанкинг остаётся 1000/150.

## Дополнительный API-кандидат

В актуальной документации доступен stable `gemini-embedding-2`: мультимодальный, 100+ языков, вход 8192 токена, 128–3072 измерения; рекомендуются 768/1536/3072. Для маленького корпуса выбрать 3072 и не добавлять отдельный поиск размерности. `gemini-embedding-001` также остаётся доступен для текста, вход 2048 токена. [Google embeddings](https://ai.google.dev/gemini-api/docs/embeddings#model-versions).

У `gemini-embedding-2` нет `task_type`: для QA используются `task: question answering | query: …` и `title: … | text: …` (`title: none`, если заголовка нет). Несколько входов в одном content могут агрегироваться в один вектор; нужно явно получать отдельный вектор на каждый чанк. Пространства разных моделей несовместимы: весь корпус переиндексируется в отдельную коллекцию. [Форматы и миграция](https://ai.google.dev/gemini-api/docs/embeddings).

По текущей странице цен текст для Embedding 2 стоит **$0.20 за 1M входных токенов**, Batch — $0.10; доступен free tier с ограничениями. Стоимость считать по Google-токенам, а не BGE-токенам. Историческую цену Embedding 001 $0.15/M из анонса не принимать за текущий тариф: на просмотренной pricing-странице отдельной строки 001 нет. Наличие модели в документации не проверяет доступность для конкретного API-проекта и его лимиты. [Google pricing](https://ai.google.dev/gemini-api/docs/pricing#gemini-embedding-2), [исторический анонс 001](https://developers.googleblog.com/en/gemini-embedding-available-gemini-api/).

## Условия честного сравнения

1. Зафиксировать прежние чанки 1000/150, gold, 142 dev-вопроса, фильтрацию языка, Dense top50 и сборку контекста. Первым этапом менять только embedding-рецепт с официальными префиксами/инструкциями, pooling и нормализацией.
2. Сохранить **BGE-токенизатор для бюджета 2048** независимо от embedding-модели. Смена счётчика одновременно со сменой embeddings изменит доступный объём контекста.
3. Для каждой модели создать отдельную коллекцию; записать revision, tokenizer revision, prompt, dtype, устройство, batch, лимит входа и хеш корпуса. Сохранить векторы и результаты для повторного анализа.
4. Сравнивать Evidence Recall/Coverage/CER отдельно в top50 и в упакованном контексте. Считать парные изменения по вопросам и bootstrap, раздельно RU/EN; отмечать регрессии, а не только среднее.
5. Только для перспективной альтернативы проверить, сохраняется ли выигрыш после прежних BM25/RRF и фиксированного reranker. Улучшение Dense не доказывает улучшение всей цепочки.

Лидерборды здесь служат отбором кандидатов. [Qwen paper](https://arxiv.org/html/2506.05176v1) опубликован в июне 2025, [E5 report](https://arxiv.org/html/2402.05672v1) — в феврале 2024; их таблицы не измеряют наш IFAB-корпус и не являются актуальным общим рейтингом на октябрь 2026. Совпадения training/evaluation-корпусов и различия протоколов не проверялись независимо. Недостаток контекста, широкая gold-разметка и потеря структуры при PDF-парсинге могут ограничивать качество независимо от embedding-модели.

## Что ограничивает текущую цепочку

Повторно разобраны 142 сохранённых per-question результата E4b `4c359a2676444bc38f68f92deaa92c83` (Hybrid RRF50 → BGE reranker → бюджет 2048). Это offline analysis прежнего запуска, не новый inference-run. Взаимоисключающие группы:

| Покрытие обязательного evidence при пороге 80% | RU, из 71 | EN, из 71 |
|---|---:|---:|
| Полное в итоговом контексте | 48 | 54 |
| Полное в пуле 50, неполное в контексте | 15 | 13 |
| Неполное даже в пуле 50 | 8 | 4 |

Новая embedding-модель может изменить и состав кандидатов, и их ранги, но большая часть оставшихся неуспехов уже содержит необходимые источники в пуле. Нельзя автоматически приписывать эти 28 случаев слабым embeddings или считать их гарантированно исправимыми reranker: минимальный достаточный контекст мог не помещаться в бюджет, а gold иногда широк. Например, FR002 RU требует положения об офсайде с продолжением на соседней странице; E4b покрывает gold на 100% в пуле, на 57,33% в контексте. FR045 RU с продолжением через границу страницы имеет 66,20% покрытия даже в пуле; это основание проверить структуру, не доказательство причины.

## Что предлагают исследования помимо смены модели

- **Контекст чанка.** Anthropic дописывает краткий контекст конкретного фрагмента перед embedding и BM25. Их заявленный выигрыш измерен по retrieval failure@20 на других корпусах; это не CER нашего проекта. Первое упрощённое испытание для IFAB — проверенные заголовки Law/section из источника, без LLM-generated summaries. Это наша адаптация идеи, а не точное воспроизведение их метода. Заголовки не берём из вопросов/gold; при отсутствии надёжной структуры сначала проверяем её извлечение. [Anthropic, Contextual Retrieval, 2024](https://www.anthropic.com/research/contextual-retrieval).
- **Отдельные фрагменты поиска и контекста.** Parent retrieval ищет дочерние фрагменты и возвращает более крупные родительские. Для нас возможен ограниченный возврат соседнего текста того же раздела после проверки, что ошибки действительно связаны с продолжением правила. Расширение остаётся в том же бюджете, пересечения удаляются; целое правило автоматически не возвращаем. [Официальный ParentDocumentRetriever](https://reference.langchain.com/python/langchain-classic/retrievers/parent_document_retriever/ParentDocumentRetriever).
- **Переформулирование запроса.** Rewrite-Retrieve-Read исследует разрыв между вопросом и поисковым запросом. Оставляем после локальных альтернатив, если аудит покажет систематические бытовые формулировки: добавляет API-стоимость и может исказить обстоятельства эпизода. [Ma et al., 2023](https://arxiv.org/abs/2305.14283).
- **Контроль результата генерации.** Рост retrieval coverage при большем контексте не гарантирует рост точности LLM; в Lost in the Middle важны объём и положение evidence. Это аргумент ограничить следующий retrieval-цикл и затем измерить ответы, а не бесконечно оптимизировать одну retrieval-метрику. Работа не тестирует нашу Gemini-конфигурацию. [Liu et al., 2023/2024](https://arxiv.org/abs/2307.03172).

BGE-M3 также поддерживает learned sparse и multi-vector retrieval; наш BM25 не использует эти выходы. Это отдельные кандидаты на будущее, сейчас добавят сразу несколько новых механизмов. [Статья M3-Embedding](https://arxiv.org/abs/2402.03216).

Дополнительно просмотрена новая `jina-embeddings-v5-text-small`: multilingual, отдельные task adapters, лицензия CC-BY-NC-4.0 и требования к PEFT/custom code. Она остаётся резервом, чтобы не расширять первый локальный цикл тремя альтернативами; это не вывод о её качестве. [Официальная карточка Jina](https://huggingface.co/jinaai/jina-embeddings-v5-text-small). У Google есть и локальное семейство EmbeddingGemma; доступ/лицензия и точная версия отличаются, в этот ограниченный план оно не включено. [Google EmbeddingGemma](https://ai.google.dev/gemma/docs/embeddinggemma).

## Предлагаемый следующий цикл

1. **Dense + Qwen3-Embedding-0.6B против E0.** Прежний корпус 1000/150, Dense50, BGE-бюджет 2048, gold и dev. Проверить официальную инструкцию, лимиты, finite/unit-normalized vectors и отдельную коллекцию; зафиксировать revision до загрузки. Один полный MLflow run и отдельная явно отмеченная smoke-проверка.
2. **Dense + multilingual-e5-large против E0.** Те же условия и официальные префиксы; не менять одновременно чанкинг, бюджет, reranker или разметку. Две альтернативы — заранее ограниченный набор, а не поиск до первого красивого результата.
3. **Взаимодействие с Hybrid/reranker.** Для одной перспективной embedding-конфигурации повторить прежние BM25, RRF60/top50 и BGE-reranker50; сравнить с E4b при B=2048. Если альтернативы не дают убедительного результата, сохранить BGE-M3 и не создавать фиктивный run уже измеренной комбинации.
4. **Один опыт по подтверждённому типу ошибки.** Перед ним проверить несколько неуспехов из таблицы: при потере названия раздела — заголовки; при разрыве продолжения — ограниченные соседи/parent. Выбрать одно изменение. Увеличение бюджета до 4096 можно сначала пересчитать из сохранённой выдачи E4b без нового embedding/search; не выдавать такой пересчёт за ускорение или улучшение при прежнем B.

На каждом шаге: CER/Recall/Coverage RU/EN в контексте и в pool50, парные улучшения/ухудшения, grouped bootstrap; время индексации, query latency, память. Дополнительные ranking-метрики допустимы как диагностика, поскольку чанки одинаковые, но chunk_v1 relevance имеет известные ограничения и не заменяет evidence-based критерий. Если используем GPU, сохраняем точные dtype/device; для сравнения скорости моделей нужен BGE-контроль на том же устройстве, старое CPU-время E0 не является таким контролем. Векторы разных моделей даже одинаковой размерности несовместимы; переиндексируются и документы, и запросы.

После ограниченного цикла зафиксировать рабочую конфигурацию и проверить генерацию Gemini/Ragas. Test не используется для отбора, gold не исправляется ради метрик; при реальной ошибке разметки — отдельная версия и повторная оценка контролей.

Не проверены загрузка новых моделей, GPU-память, latency, Google-доступ и качество на нашем корпусе. Эти неопределённости снимает следующий эксперимент, не чтение лидерборда.
