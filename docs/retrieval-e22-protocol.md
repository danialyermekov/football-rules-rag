# E22: gold-aware budget feasibility oracle

Протокол зафиксирован до smoke и основного расчёта. Только dev с обязательным evidence: 142 вопроса (71 RU, 71 EN), test не читать. Источники: FINISHED E21 `174a45eee3c243e2a7bf21be9ddd7bae` и E15 `b8b229800f4246d090eea03a4d5c9900`; top50 E15 и E21 должны совпадать по ID и содержимому, с сохранёнными оценками. Проверить хеши четырёх исходных файлов против параметров обоих runs, expectations, 142 уникальных вопроса, исходные chunks и точный replay E21 ordering/packing и evidence metrics. Проверить ревизию локального BGE tokenizer и записать SHA256 его файлов и всех входов; загрузка строго local-only.

Критерий FOUND: свидетельство — список уникальных целых чанков из сохранённого top50 в порядке E15, исходный `render_context`, `add_special_tokens=False`, не больше 2048 токенов на целой строке, и каждый locator каждого required evidence покрыт как минимум на 80% по `evidence_metrics` v2. Сохранить IDs, текстовый контекст, точные токены и метрики; повторно проверить. Использовать gold только для этого офлайн oracle, не для пользовательского retriever.

Если объединение всех 50 чанков не достигает CER, `IMPOSSIBLE_POOL`: доказанная невозможность любого подмножества и порядка при том же coverage, независимо от бюджета. Иначе baseline E21 с CER=1 сам является FOUND. Для остальных выполнить детерминированный поиск сочетаний до четырёх gold-пересекающихся чанков в порядке E15, по возрастанию размера и индексов; каждое полное покрытие проверять точной токенизацией. Поиск ограничен 2 секундами wall-clock на вопрос и 20000 сочетаниями; при завершении без свидетельства или таймауте — UNKNOWN, поскольку большие наборы, другие порядки и чанки вне этого подмножества не исключены. Не использовать сумму токенов отдельных чанков как доказательство и не отсекать ветви по длине (токенизация контекста может быть немонотонной). Время может менять найденные свидетельства при таймауте; лимит сочетаний и сортировка фиксированы, индивидуальные причины и число сочетаний записываются.

Сначала smoke на трёх первых вопросах dev с native MLflow dataset, deterministic scorer, `mlflow.genai.evaluate`, проверкой trace readback; затем полный bound на всех 142, только после успешной проверки smoke. Лимит полного запуска 20 минут снаружи процесса; в случае прерывания не выдавать незавершённый результат за полный. Вывести FOUND / IMPOSSIBLE_POOL / UNKNOWN отдельно RU/EN, E21 CER и pool-complete, а также нижнюю и верхнюю границы feasibility: FOUND и FOUND+UNKNOWN на 71. Сохранить per-question входы, результаты, hash manifest, код, протокол и summary в новом MLflow run и `tmp/e22`. Новые embedding, reranking, API, генерация и пакеты запрещены. Тесты проверяют статусы, точные budget boundary и source coordinates. Исторический gold содержит broad AND evidence; результат не является качеством retriever или оценкой обобщения.

### Recovery 2 — после воспроизведения QueuePool starvation

Full `8520e4d46f0e441ebc4a6842e9fbabc0` с `MLFLOW_DISABLE_TELEMETRY=true` и прежней конкурентностью не завершился за180s. Диагностический стек через100s показывает ожидание SQLAlchemy QueuePool при `start_trace`/`log_spans`, логи явно содержат `QueuePool limit of size 5 overflow 10 reached`. Значит, отключение telemetry не устраняет воспроизведённый сбой. После подтверждения завершения процесса run помечается KILLED, не FAILED/FINISHED задним числом.

Следующая проверка меняет только конкурентность: до native evaluate выставить безопасные defaults `MLFLOW_GENAI_EVAL_MAX_WORKERS=1` и `MLFLOW_GENAI_EVAL_MAX_SCORER_WORKERS=1`; явные переменные пользователя сохраняются и логируются. Ни scorer, ни tracing не отключать, параметры oracle и budget не менять. Новый smoke3 → full142, тот же внешний deadline180s. Unit test проверяет fail-fast окружения и worker defaults (red→green); реальная регрессия конкурентности проверяется полным native run, а не этим unit test. Таймаут и missing assessments не считать успешным результатом.
