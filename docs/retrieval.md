# Dense retrieval: BGE-M3 и локальный Qdrant

## Что реализовано

```text
chunks.jsonl → BGE-M3 dense embeddings → Qdrant Local на диске
Вопрос → та же BGE-M3 → cosine search с фильтром языка → чанки и источники
```

Используется dense-часть `BAAI/bge-m3`, размерность 1024, нормализованные векторы, cosine similarity. Sparse и ColBERT возможности BGE-M3 здесь не используются. Ревизия модели закреплена: `5617a9f61b028005a4858fdac845db406aefb181`.

Модель работает через Sentence Transformers на CPU в float32: 4 потока, batch size 4. Проверяется длина входа по tokenizer; превышение лимита приводит к ошибке вместо незаметного обрезания. Google API не используется. GPU-ускорение в этой реализации не настраивалось.

Qdrant подключён через **local mode Python-клиента с постоянным хранением на диске**. Docker daemon на машине во время реализации был недоступен. Это удобный baseline для 773 чанков; отдельный сервер, HTTP API, HNSW, многопользовательская работа и Docker пока не проверяются. Local mode блокирует одновременное открытие одного каталога несколькими процессами: сначала закройте текущую команду, затем запускайте следующую.

## Подготовка и запуск

Из корня проекта:

```powershell
uv sync --locked
uv run hf download BAAI/bge-m3 config.json modules.json config_sentence_transformers.json sentence_bert_config.json tokenizer.json tokenizer_config.json special_tokens_map.json 1_Pooling/config.json pytorch_model.bin sentencepiece.bpe.model --revision 5617a9f61b028005a4858fdac845db406aefb181 --local-dir data/models/bge-m3
uv run football-rules index
```

Загрузка включает около 2,27 GB весов. Приложение загружает модель только из локального каталога и проверяет ревизию в metadata загрузчика для весов, config и tokenizer. Для переноса модели сохраняйте также `.cache/huggingface/download` внутри каталога модели. Это проверка происхождения загрузки; приложение не пересчитывает SHA-256 всех весов при каждом старте.

Команда `index` читает `data/processed/chunks.jsonl` и печатает имя коллекции. Затем используйте это имя:

```powershell
uv run football-rules search "Мяч частично пересёк боковую линию. Он вне игры?" --language ru --collection <имя_коллекции> --k 5
uv run football-rules search "Can a player be offside directly from a throw-in?" --language en --collection <имя_коллекции> --k 5
```

На выходе — ранжированные чанки с cosine score, текстом, документом, PDF/печатной страницей и диапазонами исходного текста. **Это поиск, ещё не ответ ассистента.** Score не является вероятностью правильного ответа и пока не используется как порог отказа.

В baseline RU-вопрос ищет только по RU-чанкам, EN — по EN. Поэтому сравнение RU/EN оценивает два языка на соответствующих корпусах; это ещё не эксперимент с русским вопросом по исключительно английскому корпусу.

## Воспроизводимость индекса

- Векторизация документов и вопросов использует один `Embedder`. Интерфейс `encode` + `parameters` позволяет позже добавить другую модель без изменения Qdrant-поиска.
- Файл чанков хешируется. Хеш, параметры embedding, версия Qdrant-клиента и размер коллекции записываются в manifest.
- Имя коллекции зависит от этой конфигурации. Новые чанки или другая модель создают другую коллекцию; прежняя не удаляется.
- Полный `chunk_id` сохраняется в payload, а Qdrant point ID создаётся детерминированно через UUID5.
- Повторная индексация готовой коллекции проверяет manifest и количество точек и не вычисляет embeddings повторно.
- Manifest появляется после успешной загрузки всех точек. Прерванную загрузку можно повторить в ту же коллекцию; upsert использует стабильные ID.
- Поиск проверяет совпадение конфигурации query embedder с manifest и количество точек. Для оценки также сверяется SHA-256 файла чанков.

Модель, база и MLflow-хранилище локальны и исключены из Git. Runtime-зависимости закреплены в `uv.lock`.

## Оценка retrieval и MLflow — исторический протокол v1

С 23 октября основной протокол — [v2: объединённые evidence и бюджет контекста](retrieval-evaluation-v2.md), результаты ведутся в [общем журнале](retrieval-results.md). Ниже сохранено описание первого baseline; его метрики нельзя напрямую вычитать из v2.

Используются native `mlflow.genai.datasets.create_dataset`, `@scorer` и `mlflow.genai.evaluate`; платных LLM judges нет. Четыре детерминированных scorer считают Recall, Precision, MRR и NDCG для K = 1, 3, 5, 10.

Оценка берёт только dev-ситуации с обязательным evidence: 71 ситуация / 142 вопроса RU/EN. Четыре dev-ситуации без обязательного evidence не имеют определённого gold для ranking metrics и здесь не оцениваются. Отказ от ответа и вопросы вне корпуса будут оцениваться при появлении generation. Test-набор не запускается.

### Правило релевантности v1

Gold chunk IDs выводятся из evidence-координат, независимо от найденных результатов. Чанк релевантен, если его исходные диапазоны содержат **не менее 80% непробельных, сохранённых очисткой символов хотя бы одного обязательного evidence locator** на той же странице того же документа. Удалённые номера страниц и колонтитулы не входят в знаменатель.

Это фиксированная эвристика, а не судейская разметка релевантности каждого чанка. Она позволяет проверить, нашёл ли поиск достаточно полный эталонный фрагмент. Для вопросов с несколькими evidence релевантность одному фрагменту не доказывает достаточность всего контекста для ответа.

У baseline-чанкинга 14 из 142 вопросов не имеют ни одного gold-чанка по этому критерию. Они не исключаются из средних: все четыре метрики получают 0, а количество таких вопросов логируется отдельно. При пустом gold обычный Recall математически не определён; ноль здесь — явно выбранное правило отчёта, чтобы не скрывать ограничение chunking/qrels. Это также означает, что нужно отдельно исследовать полноту объединённого контекста, а не только отдельного чанка.

Остальные определения стандартные для бинарной релевантности чанков:

- Precision@K = число релевантных результатов / K.
- Recall@K = число найденных gold-чанков / число всех gold-чанков.
- MRR@K = обратный ранг первого релевантного чанка в первых K; иначе 0.
- NDCG@K = DCG с весом `1/log2(rank+1)`, делённый на идеальный DCG.

Перекрывающиеся чанки считаются отдельными кандидатами. Количество gold-чанков меняется при другом разбиении, поэтому эти метрики нельзя считать единственным доказательством превосходства стратегии: дополнительно понадобятся evidence coverage объединённого контекста, одинаковый бюджет контекста и generation quality. Порог 0,8 и это определение сохраняются в конфигурации оценки.

### Запуски

```powershell
# Сначала smoke/dry run:
uv run python scripts/evaluate_retrieval.py --collection <имя_коллекции> --protocol v1 --limit 3 --verify-trace

# Затем полный dev baseline:
uv run python scripts/evaluate_retrieval.py --collection <имя_коллекции> --protocol v1
```

Один запуск — один MLflow run; RU/EN-метрики логируются отдельно внутри него. Dry run — отдельный run с явным названием. Перед созданием evaluation dataset выполняется поиск существующих datasets; имя зависит от содержимого записей и gold ID. Для CPU evaluation используется один worker.

По умолчанию MLflow хранится в `data/mlflow/mlflow.db` (SQLite). Если настроен `MLFLOW_TRACKING_URI`, используется он; `MLFLOW_EXPERIMENT_ID` также учитывается. Проектный experiment по умолчанию — `football-rules-retrieval`.

В run сохраняются параметры модели и чанкинга, хеши корпуса и датасета, manifest индекса, зависимости, использованный код, тексты найденных чанков и результаты каждого вопроса. Логируются отдельные RU/EN-метрики и средняя задержка поиска вместе с query embedding; загрузка модели в эту задержку не входит. Трасса содержит CHAIN → RETRIEVER → EMBEDDING. Проверка `--verify-trace` читает сохранённую трассу после dry run, без повторного запроса к модели.

Для просмотра локального MLflow:

```powershell
uv run mlflow ui --backend-store-uri sqlite:///data/mlflow/mlflow.db --host 127.0.0.1 --port 5000
```

Откройте `http://127.0.0.1:5000`. Если порт занят, выберите другой. Сервер UI сам по себе не запускает evaluation и не пересчитывает embeddings.

## Измеренный baseline, 22 октября 2026

Коллекция: `football_a71631f65a6ba8bd0978b14e`, 773 точки. Индексация на CPU заняла около 8,5 минут; это разовая подготовка, не задержка каждого запроса.

Dry run: `2cf6234042fe4207a1acac4ca37040bb`, 3 вопроса. Проверена сохранённая трасса `tr-0afae4c18f8a1176c52e5a29a4a973a2`: CHAIN → RETRIEVER → EMBEDDING.

Полный dev run: **`bcf4cea80728477ba9ebd41093b56df5`**, статус `FINISHED`, 142 вопроса, по 71 на язык. Сама evaluation заняла около 50 секунд, без загрузки модели. Из MLflow повторно прочитаны 142 результата и проверено совпадение агрегированных метрик с сохранёнными оценками вопросов. Test-набор не запускался.

| Метрика | RU | EN |
|---|---:|---:|
| Recall@1 | 0,3005 | 0,3169 |
| Recall@5 | 0,5469 | 0,5845 |
| Recall@10 | 0,6315 | 0,7160 |
| Precision@5 | 0,1211 | 0,1268 |
| MRR@5 | 0,4157 | 0,4239 |
| NDCG@5 | 0,4412 | 0,4614 |
| Средняя задержка query embedding + search, с | 0,3057 | 0,3047 |

Это baseline без reranker и LLM-генерации. Метрики макроусреднены по вопросам; 14 вопросов без gold-чанков по порогу 80% включены с нулями. Значения Recall здесь относятся к gold-чанкам, а не к доле правильных ответов или полной совокупности необходимых оснований.

Для интерпретации результатов важно различать два слоя: evidence выбрал агент при создании датасета по PDF, а релевантные chunk IDs вычисляет код из координат evidence. Поисковая модель не задаёт себе ground truth. Вместе с тем независимой экспертной проверки evidence пока нет.

Проверки кода: 52 теста прошли, Ruff/Black и строгий mypy — без ошибок. В проверенных retrieval/metrics/embedding-модулях тестовое покрытие строк составляет 91%; это не доказательство качества поиска. Во время тестов видны предупреждения зависимостей: Qdrant Local оставляет незакрытым временное in-memory SQLite-соединение при проверке threadsafety, а MLflow с SQLAlchemy 2.1 использует устаревающую стратегию `noload`. Прикладные клиенты Qdrant закрываются; предупреждения не подавляются. Проверка веб-интерфейса MLflow не проводилась.

## Ограничения этапа

Нет генерации ответов, reranking, BM25/hybrid search, калибровки score для abstention и мультимодального анализа. Показатели retrieval не заменяют проверку правильности ответа. Эталоны датасета по-прежнему не прошли независимую экспертную проверку.

Первичные источники: [модель BGE-M3](https://huggingface.co/BAAI/bge-m3), [Qdrant Local](https://github.com/qdrant/qdrant-client#local-mode), [MLflow evaluation datasets](https://mlflow.org/docs/latest/genai/datasets/sdk-guide/), [MLflow code-based scorers](https://mlflow.org/docs/latest/genai/eval-monitor/scorers/custom/).
