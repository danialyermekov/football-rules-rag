# Протокол retrieval evaluation v2

Версия: `evidence_union_v2.0.0`. Реализация: `src/football_rules/evidence_evaluation.py`, запуск: `scripts/evaluate_retrieval.py`. Это проектная оценка по размеченному тексту, не автоматическая проверка футбольной интерпретации ответа.

## Что фиксируем

- Исходный корпус 2026/27, его хеши и текущую очистку с журналом удалённых диапазонов.
- Датасет v0.2: 71 dev-ситуация с обязательным evidence, 142 вопроса RU/EN. Четыре dev-ситуации без обязательного evidence исключены из ranking/evidence evaluation. Test не запускается.
- Исходные evidence-координаты, независимые от ID и количества чанков. Native MLflow dataset v2 содержит только вопросы, scenario ID и required evidence с locators. Chunk-level gold вычисляется отдельно только для исторической диагностики.
- Фильтр языка, модель BGE-M3, cosine search и прежний индекс из 773 чанков для E0. Никакого reranker или генерации в E0 нет.

Результат выборочной проверки 12 ситуаций: [evidence-audit-e0.md](evidence-audit-e0.md). Датасет для E0 не менялся. Он содержит широкие shared evidence и не содержит OR-групп альтернативных достаточных источников; метрики интерпретируются с этими ограничениями.

## Единица покрытия

Для locator берём непробельные символы исходного `text` в `[char_start, char_end)`, исключая уже зарегистрированные удаления очистки. Ключ позиции — `(document_id, pdf_page, character_offset)`. Для найденного контекста объединяем `source_spans` реально выбранных документов. Один символ считается один раз независимо от overlap.

Покрытие locator — доля его сохранённых символов, присутствующая в этом объединении. Нахождение в другом документе или на другой странице не засчитывается даже при совпадении offsets.

| Метрика / имя MLflow | Расчёт для вопроса |
|---|---|
| Evidence Coverage / `evidence_coverage` | Среднее покрытие locators внутри каждого evidence, затем среднее по обязательным evidence |
| Evidence Recall / `evidence_recall` | Доля обязательных evidence, у которых каждый locator покрыт минимум на 80% |
| Complete Evidence Rate / `complete_evidence` | 1, если каждый locator всех обязательных evidence проходит порог 80%; иначе 0 |
| Strict Complete Evidence Rate / `strict_complete_evidence` | То же при 100% покрытия |
| Source Redundancy / `source_redundancy` | `1 - unique_positions / total_positions` по выбранным чанкам; пустой контекст даёт 0 |

Для пустого контекста метрики покрытия равны нулю. Для вопроса без обязательного gold они не определяются и такой вопрос не входит в этот набор. Пустой или невалидный locator приводит к ошибке. Все обязательные units и все locators внутри unit соединены AND. OR-альтернативы не реализованы, поскольку отсутствуют в текущей разметке.

Агрегирование по вопросам — macro mean отдельно для RU и EN. Результаты двух языков относятся к 71 парной ситуации, а не к 142 независимым наблюдениям. Полное текстовое покрытие gold не доказывает достаточность минимального смыслового обоснования: broad evidence может требовать больше текста, чем нужно конкретному вопросу.

## Контекст с бюджетом

Основной бюджет — 2 048 токенов **tokenizer BGE-M3** ревизии `5617a9f61b028005a4858fdac845db406aefb181`. Используется `add_special_tokens=False`. Это длина контекста в общей измерительной шкале, не Gemini token usage, не полный prompt и не стоимость запроса.

Каждый чанк рендерится так:

```text
[document_id; pdf_page=...; printed_page=...]
Текст чанка
```

Между чанками — две новые строки. Подписи и разделители входят в бюджет. Tokenizer получает весь кандидатный отрендеренный контекст: сумма токенов отдельных строк может отличаться от длины их объединения.

Упаковка идёт по рангу: целый чанк добавляется, если помещается; иначе пропускается, и рассматривается следующий. Точные повторы chunk ID пропускаются. Частичные overlap остаются в тексте и занимают токены, но не увеличивают coverage повторно. Обрезания чанков нет. Записываются выбранные документы, текст, token count и причины пропуска.

Дополнительные бюджеты 1 024 и 4 096 пересчитываются из тех же кандидатов без нового поиска. Для каждого сохраняются метрики, выбранные ID, причины пропуска и token count. Больший бюджет при такой упаковке не обязан давать монотонный выигрыш: он может позволить добавить более ранний длинный чанк, вытеснив другой фрагмент.

## Диагностика и время

E0 возвращает 50 кандидатов на вопрос. Покрытие объединений первых 10/20/50 измеряется **без бюджетного ограничения**; это диагностика доступности источников, не качество готового контекста. Старые chunk-level метрики вычисляются для первых 1/3/5/10 и получают префикс `chunk_v1_`; для сравнения другого чанкинга они не являются главным критерием.

В latency входят query embedding + Qdrant search и основная упаковка контекста 2 048. Загрузка модели, чтение датасета, scorer, дополнительные диагностические бюджеты и запись итоговых артефактов не входят. Main packing timing включает его tracing span. Среднее, p50 и p95 сохраняются отдельно по языкам; используются линейные inclusive percentiles. Это замер на данной машине с observability, не production SLA.

E0 работает на CPU float32 с 4 потоками, как прежний baseline. Проверка GPU: RTX 3060 Laptop 6 GB доступна драйверу, но установлен `torch 2.14.1+cpu`, `cuda.is_available=False`. CUDA-сборка не устанавливалась; для последующего сравнения скорости на GPU потребуется контроль на том же устройстве и precision.

## Запуск

```powershell
uv run python scripts/evaluate_retrieval.py --collection football_a71631f65a6ba8bd0978b14e --protocol v2 --limit 3 --verify-trace
uv run python scripts/evaluate_retrieval.py --collection football_a71631f65a6ba8bd0978b14e --protocol v2
```

v2 — default. Исторический протокол доступен через `--protocol v1`. Один запуск — один MLflow run; dry run явно помечен. Custom scorers запускаются напрямую из репозитория через native `mlflow.genai.evaluate`, без LLM judges и без включения регистрации произвольного scorer-кода на сервере.

Run сохраняет `evaluation-protocol.json`, source/index manifest, хеши датасета и очищенных страниц, используемый код, конфигурацию и per-question результаты. Общий журнал: [retrieval-results.md](retrieval-results.md). V1 и V2 нельзя вычитать как изменение качества поиска: они оценивают разные объекты. E0 — первая контрольная точка нового протокола.
