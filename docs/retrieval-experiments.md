# План исследования retrieval

Дата изучения первичных источников: 22 октября 2026 года. Это план экспериментов, а не отчёт об улучшениях: новые индексы, reranker и платные API в рамках исследования не запускались.

## Исходная точка и принцип выбора изменений

В проекте уже есть BGE-M3 dense, Qdrant Local, 773 чанка, фильтр языка и первый dev-run на 142 вопросах. Чанкинг ограничен страницами, размер — 1 000 символов, целевой overlap — 150 символов. Конкретные результаты и ограничения описаны в [retrieval.md](retrieval.md).

Сначала различаем причины ошибок:

- доказательства нет среди кандидатов — исследуем глубину поиска, lexical/hybrid и разбиение;
- доказательство есть, но слишком низко — проверяем reranker;
- доказательство распределено между фрагментами — проверяем объединённое покрытие, границы и расширение контекста;
- найден полезный официальный фрагмент, отсутствующий в gold, — проверяем разметку, прежде чем объявлять результат ошибочным.

Последний случай реален для нашего корпуса: пояснение к иллюстрации IFAB может быть полезным источником, даже когда gold указывает на основной текст Law. Приложения и иллюстрации нельзя автоматически выкидывать как шум. Вопросы и evidence создавал один агент; независимого экспертного ревью нет. Проверка координат подтверждает происхождение текста, а не полноту набора допустимых доказательств.

## Lexical baseline и hybrid search

BM25 ранжирует текст по совпадениям терминов с учётом их частоты и длины документа; параметры `k1` и `b` регулируют насыщение частоты и нормализацию длины. Это полезный самостоятельный baseline, а не обязательное улучшение dense. [Официальное описание BM25 в Elasticsearch](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

**Гипотеза для IFAB:** точные названия процедур, номера правил и специфические формулировки могут помогать lexical-поиску. Вопрос с бытовым «лопнул» и документ с «повреждённый» показывают обратный риск: совпадений слов может не хватить. Для RU нужно явно зафиксировать tokenizer, регистр, обработку `ё`, чисел и морфологии; EN и RU нельзя сравнивать при незадокументированных разных правилах обработки. Отрицания и числа не удалять без отдельного обоснования.

Hybrid объединяет выдачи dense и lexical. Qdrant документирует RRF: объединение по рангам позволяет не складывать напрямую несопоставимые cosine и BM25 scores. Пример документации — подтверждение доступного подхода, но не доказательство поддержки каждого нового API нашей закреплённой версией Qdrant Local. Совместимость нужно проверить до реализации; для малого корпуса допустимо объединение списков на стороне приложения. [Qdrant: Hybrid Queries](https://qdrant.tech/documentation/search/hybrid-queries/)

**Первый опыт:** dense, BM25 и dense + BM25/RRF на одинаковых чанках и с одинаковым итоговым бюджетом контекста. Зафиксировать размер выдачи каждой ветви, уникальный объединённый пул, формулу RRF, веса, константу сглаживания и способ разрешения равных scores. Число кандидатов и константу RRF не называть одним параметром `k` в отчётах. Это проектный протокол, а не универсально лучшие настройки.

## Глубина кандидатов и reranking

В стандартной схеме retrieve-and-rerank первый поиск получает кандидатов, затем cross-encoder совместно обрабатывает вопрос и каждый кандидат и меняет порядок. Документация Sentence Transformers объясняет, почему дорого оценивать таким образом весь большой корпус. [Sentence Transformers: Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

**Следствие для эксперимента:** reranker не восстановит отсутствующий кандидат. Сначала измеряем покрытие evidence объединением top-10/20/50 кандидатов. Эта величина задаёт верхнюю границу покрытия, достижимого одним переупорядочиванием данного пула. При полном reranking того же пула покрытие всего пула не меняется; измениться должно качество его начала и собранного бюджетного контекста.

Кандидат для первого опыта — `BAAI/bge-reranker-v2-m3`: авторы указывают multilingual и показывают использование через `CrossEncoder`. Score после sigmoid не становится откалиброванной вероятностью достаточности доказательств. [Официальная карточка BAAI](https://huggingface.co/BAAI/bge-reranker-v2-m3)

**Проверка применимости:** multilingual не гарантирует качество русских футбольных правил; слова авторов о скорости не являются замером нашего CPU. Перед полным dev-run проверяем небольшой набор пар RU/EN: время загрузки, память, batch size, время пары, длины вопрос + чанк и отсутствие незаметного truncation. Не переносим `fp16` из примеров как готовую CPU-оптимизацию. Ревизию, precision и max length закрепляем. Модель в ходе исследования не скачивалась.

Начальный ограниченный опыт: 20 кандидатов; расширение до 50 — если измеренный candidate coverage заметно ограничивает результат. При 142 вопросах это 2 840 или 7 100 пар соответственно. Это оценка количества вычислений, не обещание времени выполнения.

## Размер, overlap и структура документа

Recursive splitter использует последовательность разделителей; размер задаётся `length_function`, overlap является целевым. В нашем baseline единица — символ, а не токен. [LangChain: recursive splitting](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)

**Проверяемые гипотезы:** маленький чанк точнее локализует тему, но может отделить исключение; большой сохраняет условия, но добавляет лишний текст. Больше overlap означает больше дублирования, а не гарантированно больше полезного контекста.

Не перебираем сразу декартово произведение настроек. Сначала два дополнительных размера вокруг baseline при фиксированном абсолютном overlap 150 символов: меняется один параметр. Затем выбранный размер с overlap 0 и 150. Относительная доля overlap при изменении размера неизбежно отличается; оба значения записываются. Обязательно записываем фактические длины, количество и долю дублей: границы страниц могут сделать запрошенные размеры похожими по результату.

Структурное разбиение группирует текст по заголовкам; LangChain демонстрирует сохранение иерархии в metadata и возможность оставить заголовки в тексте. Это механизм для размеченного Markdown, а не автоматический надёжный разбор нашего PDF. [LangChain: splitting by headers](https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter)

**Отдельные опыты после ошибок baseline:** добавить проверенный `Law → section` к embedding-тексту; затем разрешить продолжение раздела между соседними страницами. Не смешивать эти изменения с размером в одном первом сравнении. Заголовки брать из документа, не из вопроса, эталонного ответа или evidence. Добавленный текст не получает вымышленных исходных диапазонов, но занимает токены контекста.

## Расширение контекста

Parent retrieval ищет небольшие дочерние фрагменты и возвращает более крупные родительские. Так устроен `ParentDocumentRetriever` в исходном коде LangChain. [Реализация ParentDocumentRetriever](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain_classic/retrievers/parent_document_retriever.py)

Для нас более простой первый опыт — добавить соседний блок или чанк к найденному, когда разбор ошибок обнаружит потерянное продолжение. **Это гипотеза для IFAB**, а не свойство библиотеки. Ограничить тем же документом, языком и проверенным разделом; удалить повторные диапазоны; соблюдать тот же итоговый бюджет. Отдельно измерять покрытие до и после расширения. Возврат целого Law может расходовать бюджет на нерелевантные положения.

## Query rewriting и multi-query — позже

В работе Rewrite-Retrieve-Read авторы исследуют разрыв между исходным вопросом и поисковым запросом. Их результаты на QA с web search не доказывают эффект на IFAB. [Ma et al., Query Rewriting for Retrieval-Augmented Large Language Models](https://arxiv.org/abs/2305.14283)

Если останутся ошибки из-за бытовых формулировок, можно отдельно сравнить исходный запрос с исходным + одним переписанным либо несколькими вариантами. Исходный запрос сохранять; не добавлять в него неподтверждённые обстоятельства эпизода. Логировать промпт, модель, варианты, стоимость и задержку. Это дополнительный LLM-этап; до локальных BM25/hybrid/reranking он не нужен. Перевод RU-вопроса для EN-корпуса — отдельный cross-language опыт, меняющий нынешнюю постановку с фильтром языка.

## Оценка до оптимизации

Исследование Chroma предлагает оценивать найденные участки на уровне токенов, поскольку gold-документы/чанки зависят от разбиения. Это первичное исследование авторов; его конкретные победители не переносятся на наш корпус. [Chroma: Evaluating Chunking Strategies for Retrieval](https://www.trychroma.com/research/evaluating-chunking)

Наше проектное решение: сохранить исходные evidence неизменными, считать покрытие объединения координат, исключать повторы и отдельно показывать долю вопросов со всеми обязательными основаниями. Различать locator, evidence unit и вопрос; частичное покрытие страницы не означает полноту многостраничного evidence. Порог покрытия и правила объединения фиксируются до сравнения.

Для разных разбиений основной режим — одинаковый бюджет реально собранного контекста с закреплённым tokenizer. Это сопоставимость внутри опыта; BGE-токены нельзя называть фактическими Gemini-токенами. Дубли и добавленные заголовки расходуют бюджет. Нужны неизменные правила упаковки и обработки не помещающегося чанка; если допускается обрезание, coverage считают по реально оставшемуся тексту и его диапазонам. Уникальный объём evidence и фактическая стоимость контекста — разные величины.

Chunk-level MRR/NDCG/Recall полезны для одного и того же разбиения; их не используем единственным критерием победы другого чанкинга. RU/EN одной ситуации — парные наблюдения, а не два независимых кейса: при оценке разброса различий группировать по ситуации. Слабые изменения среднего проверять по вопросам и языкам, не объявлять победой без разбора.

## Ограниченный порядок работы

1. Проверить выборку ошибок и разметку; зафиксировать evidence-based протокол, версию датасета и правила бюджета.
2. Пересчитать baseline и candidate coverage на нескольких глубинах, без скачивания новых моделей.
3. На прежних чанках сравнить BM25, dense и RRF; затем отдельно reranker на выбранном пуле после CPU smoke-check.
4. Проверить два дополнительных размера и затем overlap. Отдельно проверить перспективное разбиение вместе с выбранным retrieval — взаимодействие компонентов возможно.
5. Только по оставшимся типам ошибок брать структуру/заголовки/соседей. Query rewriting и новые embeddings оставить на следующий цикл.
6. После ограниченного цикла выбрать компромисс качества и задержки, зафиксировать его и перейти к генерации. Не исчерпывать dev множеством мелких подстроек и не использовать test для выбора конфигурации.

Каждое сравнение — отдельный MLflow run с конфигурацией, SHA корпуса/датасета, ревизиями моделей, версией протокола, результатами вопросов и временем этапов. Загрузка модели и построение индекса отдельно от тёплой задержки запроса. Найденные тексты и кандидатов сохранять для аудита и повторного расчёта метрик без повторного inference; кэшированный пересчёт не выдавать за новый замер скорости.

Исследование не включает локальный benchmark reranker, установку BM25, новые метрики или исправление разметки. Улучшение каждой стратегии остаётся гипотезой до измерения на нашем dev-наборе.

Последние 14 нельзя автоматически объявлять ошибками поиска: объединённый контекст может покрывать evidence, хотя отдельный чанк не проходит старый порог.

Примеры для аудита:

- FR002 RU: top-1 на PDF 244 — официальный текст к иллюстрации офсайда; gold указывает на основной текст Law 11. Это кандидат на полезный альтернативный источник, который нужно проверить по всем условиям вопроса.
- FR004 EN: поиск возвращает текст к иллюстрации на PDF 237, gold относится к положениям основного правила. Нельзя признать фрагменты эквивалентными только по одинаковой теме.
- FR006 RU: top-1 описывает возобновления после нарушений на PDF 131, тогда как ответ требует отдельно основания для пенальти и дисциплинарной санкции. Один тематически подходящий чанк не гарантирует полный ответ.
- FR017 EN: вопрос использует `bursts`, gold Law 2 — `defective ball`, а top-1 — общий текст о возобновлениях из Law 8. Проверяем словарь и уровень конкретности; BM25 не обязан исправить несовпадение терминов.

## Зафиксированный проектный протокол v2 — к реализации

Этот раздел задаёт начальные настройки опытов. Значения 0,8, 2 048 и размеры чанков — наши заранее выбранные настройки, не оптимумы из литературы. До реализации и sanity-check они остаются планом.

### Сначала gold и неизменная единица оценки

1. Проверить 12–15 dev-ситуаций: ошибки отбора, ошибки порядка, многостраничные/многосоставные основания и несколько успешных примеров. Проверять обе языковые версии. Список ID и причины выбора сохранить до правок.
2. Для каждого основания проверить, что evidence не шире нужного утверждения и не пропускает его условия. Не укорачивать диапазоны ради роста метрик.
3. Если найден другой достаточный источник, отметить его как альтернативу, а не добавлять к обязательному AND-списку. При необходимости явно описать группы эквивалентных доказательств. Источник должен обосновывать нужное утверждение, а не просто упоминать тему.
4. Содержательные правки датасета — отдельная версия с журналом причин. После неё заново оценить все сравниваемые варианты. Нельзя сравнивать старый run с новым как улучшение поиска при разных gold.
5. Для сравнения заморозить источник, координаты evidence, исключаемые диапазоны колонтитулов/номеров и split. Gold не выводится из чанков и не строится по score модели. Независимого экспертного ревью по-прежнему нет.

Для каждого locator считаем долю его сохранённых непробельных символов, покрытых **объединением** реально переданного контекста. Ключ координат включает документ и PDF-страницу. Перекрытия считаются один раз. Если evidence unit содержит несколько обязательных locators, при проверке полноты каждый должен пройти порог; большой найденный фрагмент не компенсирует пропуск другого.

Основные метрики:

| Имя | Определение |
|---|---|
| `evidence_coverage` | Для evidence усредняем покрытия его locators, затем усредняем по обязательным evidence вопроса |
| `evidence_recall` | Доля обязательных evidence units, у которых каждый обязательный locator покрыт не менее чем на 80% |
| `complete_evidence_rate` | Доля вопросов, у которых покрыты все обязательные evidence units; главный критерий выбора |
| `complete_evidence_rate_strict` | Дополнительная строгая проверка с порогом 100%, чтобы порог 80% не скрывал недостающее условие |
| `context_tokens`, `redundancy` | Реальный объём собранного контекста и повторение исходных диапазонов |
| `latency_p50/p95` | Задержка query embedding, отбора кандидатов, reranking и сборки контекста, отдельно и целиком |

При альтернативных достаточных доказательствах используем заранее размеченную OR-группу; остальные обязательные группы остаются AND. Без такой разметки считаем метрики относительно текущего набора оснований и явно указываем неполноту gold. Строгое покрытие текста также не заменяет смысловое ревью.

142 dev-вопроса с обязательными основаниями остаются в оценке, включая 14 случаев без одиночного gold-чанка старого протокола. Четыре dev-ситуации без обязательного evidence учитываются отдельно; retrieval не даёт критерия правильного abstention без generation. RU/EN результаты выводятся отдельно и в парном сравнении по 71 ситуации. Test не используется при выборе настроек.

### Бюджет контекста и кандидаты

- Основной бюджет — **2 048 токенов закреплённого tokenizer BGE-M3**. Он уже локально доступен; это общая измерительная шкала, не оценка Gemini billing. Дополнительно показывать чувствительность при 1 024 и 4 096 токенах на тех же сохранённых ранжированиях.
- Рендер контекста, подписи источников и разделители одинаковы для всех методов и входят в бюджет. Считать токены полного отрендеренного текста, не сумму приближённых длин.
- Базовая упаковка: идти по рангу, добавлять целый чанк, если он помещается; иначе пропустить и продолжить. Не обрезать текст в первом протоколе. Сохранять выбранные и пропущенные ID, причину пропуска и фактические диапазоны.
- Точные повторы chunk ID удалять. Частичные overlap в базовой упаковке сохраняются и расходуют токены, но не дают двойного покрытия evidence. Удаление частичных повторов — возможный отдельный опыт, а не скрытая разница между конфигурациями.
- Различать `candidate_pool_size=M`, `final_top_k=K` и `context_token_budget=B`. Диагностика по K=1/3/5/10 остаётся, но при разных чанках основной критерий — фиксированный B.
- Для dense один раз сохранить top-50 и получить диагностику объединённого покрытия top-10/20/50. Это покрытие пула без бюджетного ограничения — потолок для перестановки кандидатов, не качество итогового контекста.
- Для reranker основной M=20. M=50 проверять только после измеренного выигрыша покрытия пула и оценки CPU-времени. Бюджетный контекст с reranker и без него собирать из одного и того же пула одинаковой глубины.

Sanity-check нового evaluator: evidence разбит между двумя чанками; два перекрывающихся чанка не удваивают покрытие; пропуск второй страницы оставляет unit неполным; чужой документ/страница не совпадает по числовым offsets; chunk не поместился в бюджет и не учитывается; альтернативное доказательство не превращается в новое обязательное основание.

## Матрица первого цикла

До E0 реализовать и проверить протокол выше. Цель — до девяти уникальных конфигураций, без полного перебора всех комбинаций. Бюджет B, корпус, gold, фильтр языка и BGE-M3 фиксированы. Текущий run v1 сохраняется как исторический, но не является контрольным run для v2.

| ID | Конфигурация | С чем сравниваем и зачем |
|---|---|---|
| E0 | Dense, чанки 1000/150; max pool 50 и диагностика глубин 10/20/50 | Контроль v2; отделить нехватку кандидатов от плохого порядка |
| E1 | BM25 на тех же чанках | С E0: проверить роль точных терминов, без новой embedding-модели |
| E2 | Dense + BM25, RRF | С E0 и E1: проверить дополнение методов и качество объединённого пула |
| E3 | Dense → multilingual cross-encoder, тот же выбранный M | С dense из E0 на том же M: изолировать влияние reranker |
| E4 | RRF → тот же cross-encoder, тот же M | С E2: изолировать reranker; с E3: влияние hybrid-кандидатов |
| E5 | Dense, чанки 600/150 | С E0: уменьшить только размер чанка |
| E6 | Dense, чанки 1600/150 | С E0: увеличить только размер чанка |
| E7 | Лучший из 600/1000/1600 при overlap 0 вместо 150 | Проверить полезность перекрытия и расход контекста |
| E8 | Перспективный чанкинг + перспективный retrieval из E0–E4 | Проверить взаимодействие; не объявлять сумму отдельных выигрышей гарантированной |

E1: начальные `k1=1.2`, `b=0.75`, без перебора. Отдельные RU/EN-корпуса для статистик BM25; Unicode-токенизация, casefold, явно записанная нормализация `ё`. Числа и отрицания сохраняются; stemming и stopword removal в первом опыте отключены. Это проверяемая начальная реализация, а не утверждение, что морфология RU не важна.

E2: по 50 кандидатов каждой ветви, объединение по chunk ID, RRF с равными весами и формулой `sum(1/(60 + rank))`, ранги от 1. Константа 60 — начальная настройка опыта, не предположение о default Qdrant. Сохранить полный объединённый пул и его размер; далее ограничить до того же M для сравнения с E3/E4. Tie-break — стабильный chunk ID. Совместимость API проверить; приложение может выполнить fusion без нового сервера.

E3/E4: кандидат `BAAI/bge-reranker-v2-m3`, точную ревизию закрепить перед скачиванием. Сначала 3 RU + 3 EN запроса и измерение пар при M=20. Проверить полный ввод query + chunk, лимит tokenizer, precision, память и оценить время 2 840 пар. Не запускать 7 100 пар для M=50 без предварительной оценки. На CPU не обещаем интерактивную задержку. Не сравнивать тёплое CPU-время одного варианта с GPU-временем другого как влияние только алгоритма.

E5–E7: рекурсивный splitter и границы страниц неизменны. Для каждой новой конфигурации — новый файл чанков, хеш и коллекция, прежние не удаляются. Число чанков не фиксируется. Поскольку разбиение ограничено страницей, проверить реальное распределение длин: настройка 1600 может давать мало отличий от 1000 на коротких страницах.

E8: если комбинация ухудшила результат, сохраняем этот вывод и раздельные варианты. Это ограниченный поиск хорошей конфигурации, не поиск глобального оптимума. Если E7 или E8 полностью повторяют уже проверенную конфигурацию, не создаём фиктивный новый inference-run.

## Что делать после первого цикла

Выбирать следующий опыт по оставшимся ошибкам:

| Наблюдение | Следующая проверка |
|---|---|
| Правило потеряло название при разбиении | Добавление проверенных заголовков Law/section к embedding-тексту |
| Условие и исключение разнесены границей страницы | Разбиение по структуре с разрешённым продолжением между страницами одного раздела |
| Нужное место найдено, соседнее условие не попало в контекст | Соседний блок / parent expansion при том же B |
| Бытовая формулировка систематически не соответствует тексту | Query rewriting / multi-query с отдельным учётом Google API стоимости |
| Недостаточно терминов RU при сильном EN | Проверка морфологии BM25; затем отдельный cross-language опыт |

Не начинать с fine-tuning, одновременной смены embedding-модели и chunking, семантического chunking через LLM, фильтра score для отказа или настройки HNSW. В текущем Qdrant Local исследуем качество поиска, а не ANN-параметры сервера. Эти работы добавляются только под установленную причину ошибки.

## MLflow и критерий решения

Один experiment `football-rules-retrieval`, один run на уникальную конфигурацию. В run хранить parent/control run ID, версию gold и evaluator, хеши PDF/очищенного текста/чанков, конфигурацию splitter и lexical tokenizer, ревизии моделей, M/K/B, tokenizer бюджета, renderer/packing policy, candidate IDs/scores, фактически переданные диапазоны, per-question метрики, статистику языка и типа вопроса, время/память/стоимость этапов.

Для сравнения сохранить парные изменения на одних ситуациях и 95% bootstrap-интервал разницы с resampling по scenario ID, например 2 000 повторов с seed 42. Обе языковые версии одной ситуации переносить вместе. Это показывает неопределённость на нашем небольшом dev-наборе, но не исправляет синтетичность данных и возможные ошибки gold.

Главный ориентир — `complete_evidence_rate` при B=2048. Дополнительно смотреть coverage/recall, разницу RU/EN, p50/p95 задержки, конкретные ухудшения и долю лишнего/повторяющегося контекста. Если различие мало или неубедительно, предпочесть более простой/быстрый вариант и не заявлять доказанное превосходство. После первого ограниченного цикла зафиксировать выбранную конфигурацию и перейти к Gemini + оценке генерации Ragas; не добиваться произвольного целевого Recall бесконечной настройкой dev.
