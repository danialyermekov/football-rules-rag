# Football Rules evaluation dataset v0.2

Синтетический текстовый набор для RAG по IFAB 2026/27: **100 ситуаций / 200 вопросов**. Одна JSONL-строка содержит ситуацию с двумя языковыми версиями. Это проверенный агентом черновик для разработки и ревью; независимой экспертной проверки нет. Подробнее об архитектуре и результатах: [архитектура](../../docs/architecture.md), [сводка экспериментов](../../docs/experiments-summary.md).

## Файлы

- `scenarios.jsonl`: вопросы, эталоны, критерии и ссылки на доказательства.
- `evidence.jsonl`: 83 единицы доказательств; каждая связывает один смысловой источник с фрагментами английского и русского документов.
- `manifest.json`: версия набора, происхождение, количества и контрольные суммы.
- [Источники и SHA-256 PDF](../../docs/source-manifest.json).

## Как создано и что проверено

Ситуации и ответы написаны AI coding assistant в этой сессии по положениям локальных PDF; внешние платные API для генерации не вызывались. Первые 12 перенесены из пилота с сохранением вопросов и ответов; критерии разложены на смысловые пункты и переведены на оба языка. В v0.1 добавлены 48 ситуаций, в v0.2 — ещё 40. Набор затрагивает все 17 правил; полноты покрытия подразделов это не означает.

Новая часть FR061–FR100 содержит обычные вопросы, разговорные и неявные формулировки, ошибочные предпосылки, недостаток данных и спорные случаи применения правил. Примеры: первое касание мяча при отборе, направление передачи при офсайде, умышленная игра защитника против рикошета, неподвижная рука, место нарушения относительно линии штрафной, момент обманного движения при пенальти и отсутствие влияния раннего входа. Когда условия не позволяют вынести решение, эталон требует объяснить критерии и запросить недостающие факты, а не выдумывать их.

Агент сверил основания ответов по тексту соответствующих положений EN/RU. Это проверка тем же агентом, который писал примеры, поэтому возможны общие ошибки автора и проверяющего. Статус каждой записи — `agent_source_checked_not_expert_reviewed`. Проверка координат и хешей не проверяет правильность футбольной интерпретации или качество перевода. Визуально PDF ранее проверены выборочно; полного визуального аудита нет.

## Структура записи

| Поле | Значение |
|---|---|
| `id` | Стабильный ID ситуации FR001–FR100 |
| `scenario_group` | Группа близких ситуаций; при разбиении не разделять её между dev/test |
| `edition` | Редакция источников 2026/27 |
| `split` | 75 ситуаций `dev` и 25 `test`; RU/EN остаются вместе |
| `question_type` | Ожидаемый характер ответа |
| `questions` | Объект с `ru` и `en`; при эксперименте выбирается только один вопрос |
| `reference_answers` | Эталонные объяснения на двух языках; допустимы другие правильные формулировки |
| `must_include` | Обязательные смысловые пункты, не требования буквального совпадения |
| `must_not_claim` | Примеры существенных ошибок; список не исчерпывающий |
| `required_evidence` | Все перечисленные единицы необходимы для обоснования ответа; это AND-список |
| `related_evidence` | Только связанный материал; не считать доказательством отсутствующего ответа |
| `review_status`, `provenance` | Авторство, статус проверки, происхождение из пилота |

Состав по типам: 76 `answerable`, 7 `insufficient_information`, 11 `conditional_answer`, 6 `out_of_scope`. У out-of-scope `required_evidence` пустой: такой вопрос исключается из обычного Recall@K и оценивается по обоснованному ограничению ответа. У insufficient-information есть релевантные критерии правил, хотя данных об эпизоде недостаточно для решения.

Сохранена пропорция 75/25: 75 ситуаций (150 вопросов RU/EN) отнесены к dev, 25 (50 вопросов RU/EN) — к test. Dev содержит 58 answerable, 4 insufficient_information, 9 conditional_answer и 4 out_of_scope. Test содержит 18 answerable, 3 insufficient_information, 2 conditional_answer и 2 out_of_scope. Старое назначение всех FR001–FR060 сохранено; из 40 новых ситуаций 30 добавлены в dev и 10 в test. Близкие варианты существующих групп наследуют их часть. В dev сохранены 12 пилотных ситуаций и все связанные с ними группы.

Разбиение выбрано вручную до настройки RAG, с учётом групп, тем и типов ответа; это не случайная репрезентативная выборка. Dev затрагивает все 17 правил; test не затрагивает правила 15 и 17. Не переносим уже использованные dev-группы ради формального покрытия test. Test предназначен для итоговой проверки после выбора настроек на dev. Не подбирать на нём chunking, retrieval или prompt; после систематического использования его ошибок при настройке он перестаёт быть отложенной проверкой. Весь набор открыт в версии для чтения, поэтому это holdout по использованию в экспериментах, а не скрытый внешний benchmark.

RU/EN и перефразировки одного примера нельзя разводить между dev/test. Пересечение исходных правил между частями допустимо: мы проверяем новые вопросы к одному корпусу, а не способность отвечать по невиданным документам. Группировку следует дополнительно проверить при расширении набора. На 25 тестовых ситуациях один промах меняет долю успеха по ситуациям на 4 процентных пункта; RU/EN нельзя считать независимыми наблюдениями.

## Привязка к исходному тексту

У единицы доказательства есть `section` и `locators.en` / `locators.ru`. Языковые версии — альтернативные подтверждения одного положения, а не требование найти оба языка сразу. Для EN-only поиска используем английские координаты даже при русском вопросе. Для RU-only — русские. В смешанном корпусе не считаем повторное нахождение перевода дополнительным доказательством.

Каждый locator содержит ID документа, физический номер PDF-страницы с 1, напечатанную страницу, диапазон символов и SHA-256 фрагмента. `section` действует в пределах указанной редакции; межсезонная стабильность нумерации не предполагается.

Диапазоны считаются в **локальном нормализованном снимке страниц** `data/processed/reference-pages.json`: текст pypdf на каждой странице преобразован через `' '.join(text.split())`, без Unicode-нормализации. `char_start` включён, `char_end` исключён; единица — Unicode code point Python, не байт. Хеш снимка записан в manifest. Повторное извлечение обоих PDF с `pypdf==6.21.2` и `fonttools==4.67.0` проверено: нормализованные страницы полностью совпали со снимком. После произвольной смены парсера совпадение координат не гарантируется.

Снимок сериализуется в UTF-8 без BOM, с LF и завершающим переводом строки. Для JSON/JSONL-артефактов с контрольными суммами LF закреплён в `.gitattributes`, чтобы Git не менял байты при checkout на другой системе.

Исходники, снимок и полный текст не включаются в Git. Восстановление снимка из тех же PDF описано ниже; если его хеш не совпал, нужно выяснить причину, а не автоматически принимать новые координаты. Эти координаты не относятся к будущим очищенным chunks: ingestion должен сохранить сопоставление с исходником или потребуется новая проверенная привязка.

Некоторые подтверждения состоят из нескольких страниц и включают окружающий текст. Любое пересечение с диапазоном ещё не доказывает релевантность chunk: он должен содержать необходимое положение, включая существенные условия. Все подтверждения — достаточные проверенные основания для наших эталонов, а не исчерпывающая разметка всех релевантных мест корпуса. Перед строгим chunk-level Precision/Recall нужно оценить альтернативные найденные фрагменты; отсутствие фрагмента в разметке само по себе не доказывает нерелевантность.

## Проверка

Из корня проекта, без дополнительных зависимостей:

```powershell
python scripts/validate_dataset.py
python -m unittest discover -s tests -v
```

Проверить также локальные PDF, снимок и координаты:

```powershell
python scripts/validate_dataset.py --check-sources
```

После обычного клонирования последний режим потребует локальные исходники и тот же снимок. Тест целостности координат пропускается при отсутствии снимка; остальные тесты работают без PDF. Скрипты используют assertions: запуск с `python -O` не поддерживается.

После загрузки PDF по путям и SHA-256 из source-manifest снимок можно восстановить из PowerShell в корне проекта. Команда использует временное окружение uv, не меняя зависимости приложения:

```powershell
@'
import hashlib, json
from pathlib import Path
from pypdf import PdfReader
sources = json.loads(Path('docs/source-manifest.json').read_text(encoding='utf-8'))
for s in sources:
    assert hashlib.sha256(Path(s['local_path']).read_bytes()).hexdigest() == s['sha256']
pages = {s['language']: [' '.join((p.extract_text() or '').split()) for p in PdfReader(s['local_path']).pages] for s in sources}
content = (json.dumps(pages, ensure_ascii=False, indent=2) + '\n').encode('utf-8')
expected = json.loads(Path('data/evaluation/manifest.json').read_text(encoding='utf-8'))['source_snapshot']
assert hashlib.sha256(content).hexdigest() == expected['sha256']
target = Path(expected['local_path'])
target.parent.mkdir(parents=True, exist_ok=True)
target.write_bytes(content)
'@ | uv run --no-project --with 'pypdf==6.21.2' --with 'fonttools==4.67.0' python -
```

Валидатор проверяет ID, обязательные поля RU/EN, точные дубликаты вопросов, ссылки, покрытие 17 правил, целостность split-групп, размеры и хеши. Тесты дополнительно проверяют отклонение намеренно испорченных данных. Эти проверки не вычисляют retrieval/generation metrics и не заменяют смысловое ревью.

## Использование в будущих экспериментах

В RAG передаём только вопрос выбранного языка и найденный контекст. Эталоны, рубрики и IDs требуемых доказательств остаются у evaluator и не индексируются вместе с правилами. Отдельно сравним LLM с эталонным контекстом и с результатом реального retrieval.

Поиск оцениваем по необходимым доказательствам и рангу, отдельно от качества ответа. После появления chunks построим их соответствие источнику и проверим релевантность. Дубликаты и переводы не должны искусственно увеличивать покрытие. При нескольких обязательных основаниях одного MRR недостаточно: нужно проверять полноту найденных доказательств. При сравнении chunking учитываем и одинаковое K, и бюджет контекста.

Ограничения v0.2: небольшой синтетический набор с преобладанием answerable-вопросов; некоторые формулировки специально подробно задают условия и проще естественных пользовательских запросов. Не включены реальные изображения, другие сезоны и регламенты соревнований. Упоминания кадров в текстовых вопросах не являются визуальными входами. 200 языковых вопросов — это 100 зависимых пар ситуаций, не 200 независимых наблюдений. При сравнении языков используем парный анализ, при оценке неопределённости — группы ситуаций. Разговорные формулировки написаны агентом, а не собраны у пользователей. Первый retrieval baseline измерен на dev; качество генерации и итоговая проверка на test пока не оценивались.
